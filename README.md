# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/*.up.sql` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`
- `GET /api/v1/notifications` — список записей утренних напоминаний за дату (`?date=`, по умолчанию сегодня UTC)

## Проектные решения

Учтённые пользовательские сценарии:

- создать обычную задачу без периодичности (`none`);
- создать периодическую задачу одного из 4 типов и получать её в списке на нужные даты;
- обновить существующую задачу и сменить тип периодичности;
- получить задачи на конкретный день через `GET /api/v1/tasks?date=YYYY-MM-DD`;
- получить утренний дайджест напоминаний за дату через `GET /api/v1/notifications?date=YYYY-MM-DD` (записи создаёт фоновый процесс раз в сутки).

Заложенные ограничения:

- `every_n_days` только положительное целое число;
- `monthly.day_of_month` в диапазоне `1..31`;
- `specific_dates` должен содержать хотя бы одну дату, даты дедуплицируются;
- `month_day_parity.parity` только `even` или `odd`;
- при невалидных входных данных API возвращает `400 Bad Request`.

Обоснование решений:

- периодичность хранится как шаблон в одной записи задачи (без материализации отдельных экземпляров), чтобы не усложнять схему и синхронизацию статусов;
- фильтрация по дате выполняется на стороне SQL, чтобы сразу отдавать релевантный список из БД;
- DTO отделены от домена для контроля HTTP-формата (`specific_dates` как `YYYY-MM-DD`) независимо от внутренней модели;
- неоднозначные правила зафиксированы в разделе «Допущения» для прозрачности проверки задания;
- утреннее напоминание: один раз в сутки (UTC) для всех задач, которые «активны» на этот день по правилам периодичности и ещё не в статусе `done`; дубликат на пару (задача + день) не создаётся.

## Периодические задачи

В `POST/PUT /api/v1/tasks` добавлено поле `recurrence`.
```json
{
  "title": "Ежедневный обзвон пациентов",
  "description": "Утренний обзвон",
  "status": "new",
  "recurrence": {
    "type": "every_n_days",
    "every_n_days": 2
  }
}
```

Поддерживаемые типы:

- `none` — обычная непериодическая задача (значение по умолчанию);
- `every_n_days` — каждый `n`-й день (`every_n_days > 0`);
- `monthly` — в конкретный день месяца (`day_of_month` в диапазоне `1..31`);
- `specific_dates` — только в перечисленные даты (`specific_dates` в формате `YYYY-MM-DD`);
- `month_day_parity` — только по чётным/нечётным числам месяца (`parity`: `even|odd`).

Проверка задач на конкретную дату:

```text
GET /api/v1/tasks?date=YYYY-MM-DD
```

## Утренние напоминания

Раз в сутки в момент `REMINDER_AT_UTC` (по умолчанию `08:00`, часовой пояс UTC) сервис создаёт записи в таблице `notifications` для открытых задач (`status != done`), попадающих в выборку «на сегодня» по тем же правилам, что и `GET /api/v1/tasks?date=`.

Просмотр:

```text
GET /api/v1/notifications?date=YYYY-MM-DD
```

Переменные окружения:

- `REMINDER_ENABLED` — `true` / `false` (по умолчанию `true`);
- `REMINDER_AT_UTC` — время срабатывания в формате `HH:MM` (UTC), по умолчанию `08:00`.

## Допущения

- Для DTO выбран вариант с явным отделением от домена: `specific_dates` в HTTP-контракте принимается как `[]string` в формате `YYYY-MM-DD` и парсится в handler перед usecase.
- Задачи с `recurrence_type = none` возвращаются при любом `?date=`, так как они не привязаны к конкретной дате и считаются актуальными всегда.
- Если указан день `monthly`, которого нет в месяце (например, `31` в феврале), задача в этом месяце не появляется.
- Для `every_n_days` точка отсчёта — `created_at`, для дат раньше `created_at` задача не возвращается.
- Периодичность хранится в записи задачи как "шаблон", отдельные экземпляры в БД не создаются.
- Для `specific_dates` даты нормализуются до UTC (время отбрасывается).
- Уведомления хранятся в БД (не email/push); канал доставки вне scope.
